# Architecture

> A reference for navigating the code. The rules are in `CLAUDE.md`; here is the map: the stack, data flows, the model, what each file is responsible for, how-tos and the test layout. When you add, remove or rename files, components, hooks or exported types, update the matching section; the test `tests/docs/architecture.test.ts` checks that every path here exists and every `src/` file is mentioned.

## Stack decisions

| What | Why it was chosen |
|---|---|
| SQLite via `node:sqlite` | Built into Node, no native build; the file lives in the `/data` volume; data is entered in the "Records" section, in an emergency through `sqlite3` |
| Hono + `@hono/node-server` | A single file `dist/server/main.js`: the JSON API under `/api/` (the core's routes in `src/server/app.ts` and the sign-in ones it mounts, each module's own `/api/<…>` through `ServerModule.api`), the connector's `/.well-known/oauth-*`, `/oauth/*` and `/mcp` (outside `/api/`, `ServerModule.routes`), the hourly run of modules, and static files |
| Login | Web-managed `password` or `telegram` in `app_settings`; fresh installations open a password setup window. Environment-only `AUTH_MODE=none` temporarily disables sign-in while preserving stored settings; `AUTH_MODE=demo` selects the isolated public demo. `src/server/auth.ts`, `src/server/authSettings.ts`, `src/server/loginAttempts.ts` |
| Domain layer (`src/domain/`) | Pure functions shared by the server and the browser: one source of truth for the dashboard and the questions for Claude |
| ECharts + echarts-for-react | Best financial chart types (candlestick, zoom, sankey). SciChart.js was rejected: overkill, $1500/yr license |
| TanStack Query | Caches the `/api/snapshot` response; `staleTime: 5min` so it isn't refetched on re-renders |
| Tabler Icons | The same icons as in Vuexy; MIT. Dynamic icons go through `createElement` |
| Own router | `src/lib/router.ts` (History API + `useSyncExternalStore`), routes in `src/routes.ts`; the server serves the SPA on any path |

## Data flow

```
SQLite (DATA_DIR/finance.sqlite: the data tables of DATA_TABLES in src/domain/journal.ts, re-exported by rows.ts, including the reference tables currencies and members and the manual rates fx_manual_rates; + service, settings and module tables such as fx_rates, change_log and closed_months: every table in docs/schema.md)
  → src/server/data.ts loadAll(db): the rows, the list of closed months, the project's currencies, the family members (`members`, by rowid: the stable order of tag colours, `snapshot.members`) and the family parameter `trackFlows` (readTrackFlows: `app_settings.track_flows`, on unless '0')
  → src/server/fx.ts ensureRates(): rates of the currencies the snapshot needs (requiredRateCurrencies) per date from Frankfurter (FX_API_URL), cached in fx_rates, with the manual rates of fx_manual_rates on top; served as units per 1 USD; offline (createApp's ratesOnline: false, a demo sandbox) nothing is downloaded
  → src/domain/snapshot.ts buildSnapshot(): reads no flows while `trackFlows` is false (`withoutFlows`); converts every amount to the base currency at the rate of its own date; closed month, warnings
  → GET /api/snapshot?currency=XXX (the currency of the header switch, src/lib/currencyState.ts)
  → useSnapshot() + src/lib/snapshotSelectors.ts
  → React pages
Writes: /api/admin/* → src/server/rows.ts → guarded preflight → table + change_log in one synchronous transaction
Reminders: src/server/schedule.ts once an hour → runScheduledModules (app.ts) → modules → src/modules/reminders/reminders.ts runScheduled → Telegram Bot API;
  settings: /api/reminders* and Settings → Notifications (`/settings/reminders`)
The bot: while the sign-in runtime has a bot token (TELEGRAM_BOT_TOKEN or the one saved in Settings), src/server/bot/supervisor.ts keeps one src/server/bot/reader.ts long-polling Telegram, restarting it when the token changes → src/server/bot/dispatch.ts → the core's
  handlers (src/server/bot/signIn.ts: invite links and sign-in confirms), then each module's onBotUpdate (advisor: the council's presses and comments, src/modules/advisor/council/bot.ts; reminders: the /start that links a chat); the family server only
Account edits: /api/accounts/* → src/server/accountOperations.ts: authoritative server selection, guarded atomic rows/dependencies/journal writes
Loan edits: /api/loans/:rowid → src/modules/loans/server.ts → src/modules/loans/operations.ts: guarded atomic loan and dependency writes
Property edits: /api/real-estate/update and /delete → src/modules/real-estate/server.ts → src/modules/real-estate/operations.ts: guarded atomic shared fields/deletion across all stored valuations
Month close: /api/month-close* → src/server/monthClose.ts: the month draft; closing writes balances, flows,
  the journal and the mark in closed_months in one batch; /api/month-close/history (POST, POST /preview, DELETE) → src/server/historyImport.ts:
  the months before the wizard from a spreadsheet; buildRenameLoan contributes historical-payment journals and draft renames to guarded loan edits
Static: dist/client, SPA fallback (src/server/static.ts)
`public/` is copied by Vite into dist/client as is (favicon.svg; theme-init.js, the blocking anti-flash theme script that index.html loads in `<head>`: the CSP has no inline scripts; manifest.webmanifest with icon-192.png, icon-512.png, icon-maskable-512.png and apple-touch-icon.png, rendered from the logo, which make the app installable: no service worker, nothing cached offline; `tests/config/pwa.test.ts` checks them).
Auth: /api/auth* → src/server/auth.ts (GET /api/auth carries the setup state, `setup`, for a signed-in person; the demo router has none; `auth.setup === 'pending'` → src/components/SetupGate.tsx draws the standalone setup wizard); requireAuth closes the rest of /api/*. The live sign-in state (`AuthRuntime`, src/server/authSettings.ts) is built once in main.ts and passed to createApp, the bot dispatcher and runScheduledModules; modules get it only through their contexts (`api`, `routes`, `scheduled`, `onBotUpdate`: `auth`), never from `config`
```

Texts: the domain and the server do not word anything for the user. The domain returns warnings, problems and metric facts as locale keys with params (`MsgParams`), the server answers errors with a code and params (`{ error: { code, params? } }`), and the client translates all of it with i18next (`warnings.<code>`, `errors.<code>`, `metrics.<key>.*`). The Telegram messages are the exception: the server words them in the family language (`app_settings.language`, read with `readFamilySettings`).

## Data model

The full schema (columns, keys, indexes and the rules of direct `sqlite3` edits) is in `docs/schema.md`. Data is entered in the application, in the "Records" section.

| Table | Frequency | Role |
|---|---|---|
| `assets` | Monthly | Account balances, the last day of the month |
| `monthly_cashflow` | Monthly | Income and expenses per account, the first day of the month |
| `goals` | Quarterly | The family's goals and FIRE |
| `real_estate` | Yearly | One row per property valuation |
| `loans` | Once | The loans |
| `loan_early_payments` | On an early payment | Early repayments, read by the schedule |
| `loan_payments` | Monthly, when a month is closed with Loans and Income and expenses on | What was paid on each loan; written only by the wizard |
| `spending_categories` | When the family sets up categories | The category list for income and expenses (`flow`: `expense`, `active`, `passive`; `one_off`), with the reserved `loan_payments` row |
| `flow_lines` | Monthly, one row per account and category | Lines by category allocating an account's month totals (keyed like its `monthly_cashflow` row, in its currency; never above the total) |
| `category_spending` | Monthly, one row per category and free source | Spending by category of a card or cash that is not an account |
| `manual_mandatory_spending` | When the family types it by hand | The mandatory monthly spending, one row |
| `parameters` | Yearly | Named numbers such as `inflation_rate` |
| `currencies`, `members` | When edited in Settings | Reference lists for forms |
| `fx_manual_rates` | When the family sets a rate | The family's own exchange rates |
| `fx_rates` | When a snapshot needs a rate not cached yet | Server cache of downloaded rates |
| `change_log` | On every write | The journal ("Change history") |
| `closed_months` | When a month is closed | The months the dashboard sees |
| `month_drafts` | While a month is being filled in | The wizard's draft |
| `month_draft_revisions` | Every draft lifecycle write, retained after close | Internal stale-write counter |
| `account_closings` | When an account is closed in the wizard (one row per closing: a reused name may be closed again) | The last month an account is asked for |
| `reminder_settings` | One row | The Telegram reminder schedule |
| `app_settings` | On a settings change | Family-wide settings (language, currency, `track_flows`) and the sign-in rows |
| `users` | When a family member gets an account | Who may sign in, with which rights |
| `oauth_clients`, `oauth_tokens` | When Claude connects | The advisor connector's credentials |
| `advisor_settings`, `proposals`, `proposal_versions`, `proposal_votes`, `proposal_messages` | When the advisor's settings change, Claude sends a proposal, the family votes, or a Telegram message is delivered | The advisor's council |
| `schema_migrations` | Legacy installations only | Preserved historical bookkeeping; new databases record their version in `PRAGMA user_version` (`SCHEMA_VERSION`) |

The payment schedule is built in `computeSchedule()` (`src/domain/loans.ts`) from `loans` and `loan_early_payments` (the early payments' `strategy`, `new_payment` and `principal_credit`: `docs/schema.md`) and locked by figures recorded from it (test `tests/domain/loans.test.ts`).

The financial health metrics are computed in `src/domain/health.ts`.

Downloaded rates for each date and currency are in `fx_rates`, the family's own in `fx_manual_rates`; conversion is in `src/domain/fx.ts`.

## Monthly update workflow

At the start of each month, close the previous one with "Close month". Months are closed strictly in order; skipped ones wait in the queue.

| Table | Frequency | Action |
|---------|--------------|----------|
| `assets` + `monthly_cashflow` | Every month | The wizard: the balance at the end of the month and three flow numbers for each account; zero is a value, an empty field is not. Written as a whole on "Close <month>" |
| `goals` | Quarterly (Jan/Apr/Jul/Oct) | "Goals → Edit goals": update the `current` field of each goal |

### The monthly_cashflow format

One row per bank account per member per month. Date = the first day of the month.

| date | bank | member | active_income | passive_income | expense | currency |
|---|---|---|---|---|---|---|
| 2026-05-01 | Quillmark Bank | Robin | 6890 | 0 | 5280 | USD |
| 2026-05-01 | Brisaluna Bank | Noa | 3520 | 0 | 2140 | EUR |
| 2026-05-01 | Lumiora Bank | Robin | 41000 | 0 | 33500 | RUB |

- `active_income`: salary, freelance, other earned income
- `passive_income`: dividends, coupons, rent
- `expense`: all expenses from this account for the month (a positive number)

## Adding a new module

1. The key goes into `MODULE_KEYS` (`src/modules/types.ts`). A module has no switch: it is present from the release that adds it, and its pages show their empty states until there is data

### Where a module's interface goes (the module rule)

"Records" in this document means the screens with `section: 'data'`: they enter data and have no currency switch. The side menu has no group of that name since the topic menu: `group` places a route in the menu, `section` is its frame.

1. **New data**: a screen for entering it, a route with `section: 'data'`, as a tab of its topic (`area`). A topic that is its own question and holds its own records can be one menu item with `section: 'data'` and a `group`: Loans.
2. **A new view on an existing question**: a section or slot on that page, with no menu item: Real estate is rows in Assets, Claude is the ✨ buttons.
3. **A new question**: its own page with `section: 'dashboard'` and a menu `group` (Income and expenses, Goals, Financial health); if it deserves a place in the phone's bottom bar, `bottomBar` with a number after the existing ones (the core has 10–30, the modules 40–80) and `bottomBarTitle` when its name is long.
4. **Settings of its own**: a Settings tab, a route with `section: 'settings'` and `area: '/settings/general'` (Reminders, `/settings/reminders`).

The slots of a module (`ClientModule`): `routes`, `overview.kpis` (cells of the KPI row on Overview) / `overview.cards` (cards of its grid), `overview.todo` / `overview.todoHook` (the "To do" rows on the menu's second floor), `assetRecords`, `accountDetail` (a block of an account's detail on Accounts).

The routes (`CORE_ROUTES` plus the modules'; `routesFor({ demo })` returns them by section and `order`, in the demo without the `notInDemo` modules'):

`section` is the frame a page is drawn in, and `group` is where the menu lists it (`main`, `money`, `planning`, `settings`). A group's name shows when it holds at least two items, and `main` never shows one.

## Adding a translation key / a language

English (`src/locales/en-US.json`) is the source of the key set and the fallback; `tests/i18n/locales.test.ts` checks that English and Russian have the same keys and the other languages no key English lacks (they may lag behind and fall back to English: `docs/translating.md`), the plural forms of its language, the same placeholders and markup tags, no value copied from English (except `tests/i18n/sameAsEnglish.ts`), and that every English key is used in `src/`; the same for every locale chunk (`src/locales/<chunk>/`), whose keys must not repeat the main files.

1. **A key**: add it to English and Russian at the same path (copy existing Russian verbatim, write the English fresh) and translate it into the other five in the same change with the glossary of `docs/translating.md` (an outside contribution may leave them to Weblate); reuse `common.*` instead of a duplicate. Components call `useTranslation()` (`t` from `src/i18n/client.ts` outside components; components above `AppShell` must use the hook to re-render on a switch). A sentence with markup or a value inside is one key with tags and `{{placeholders}}`, drawn by `<Trans i18nKey components values>` (`nav.dataFor`, `cards.goal.amount`), never fragments glued in JSX. A key built from a template (`` t(`warnings.${code}`) ``) counts as used through its prefix. JSX text and the attributes `title`, `aria-label`, `placeholder`, `alt`, `label` may not hold literals (`i18next/no-literal-string` in `eslint.config.js`, for `src/**/*.tsx`); allowed are strings without letters (`—`, `%`, `×`, digits), ISO currency codes and IANA time zones as input examples; the product name `Monido` in the sidebar logo is a constant, the same in every language
2. **A plural key**: `<base>_one` and `<base>_other` in English, `_one`, `_few`, `_many`, `_other` in Russian (the categories of `Intl.PluralRules`), called with `{ count }`
3. **A lazy page's key** (one that only a lazily loaded page renders): it may go into a locale chunk, `src/locales/<chunk>/<lang>.json` in every language at the same path as in the main files (same `translation` namespace, so `t()` calls do not change); the route's page is `lazyWithChunks(() => import(…), '<chunk>')` (`src/i18n/lazyWithChunks.ts`, as in `src/modules/advisor/client.tsx`), which loads the page and the chunk together. Every Records and Settings screen is drawn inside `DataPage`, which AppShell loads with the `records` chunk, so a key only those screens use goes into `src/locales/records/` with no route change. `tests/setup.ts` loads `records` for every test; a test that renders an Advisor page directly loads `advisor` first. `tests/i18n/chunkKeys.test.ts` reads the import graph and fails when a chunk key is used by a file that something not loaded with that chunk reaches: the initial bundle, or a page loaded without it (a dashboard page for `records`, any page but the Advisor ones for `advisor`); the pages of the Records and Settings routes count as loaded with DataPage's chunks, and the server with every chunk (familyT merges them all, so a bot text may live in a chunk, as the advisor's `modules.advisor.bot.*`). A key that the shell, the menu, the Modules card, a toast outside the page or `errorMessage()` may need (route titles, `modules.<key>.title`, `errors.*`) stays in the main files. A new chunk: its name in `LocaleChunk` and a loader per language in `src/i18n/chunks.ts`
4. **A language**: `src/locales/<code>.json` (it may start partial: missing keys fall back to English) (month names in `dates.*` and the month-year order in `dates.monthYear`, the plural forms of the language), the code in `LANGUAGES` and a loader in `LOADERS` (`src/i18n/languages.ts`), and `src/locales/<chunk>/<code>.json` with its loader in `src/i18n/chunks.ts` for every chunk. The language menus (names from `languageName`) and the browser-language match pick it up; Telegram reminders can then be sent in it (the family language). Also: a column in the glossary of `docs/translating.md`, the language's same-as-English keys in `tests/i18n/sameAsEnglish.ts`, and the language in README and the user guide
5. **A server error code**: throw `new InputError('<code>', status, params)` (or answer `errorJson('<code>', status, params)`), the client shows `errors.<code>` with the params (`src/lib/api.ts`). Add `errors.<code>` to English and Russian: `tests/i18n/errorKeys.test.ts` finds the codes in `src/` and fails when `en-US.json` lacks one (`locales.test.ts` then requires it in `ru-RU.json`). Module codes are namespaced (`reminders.no_chat` → `errors.reminders.no_chat`)
6. **A domain message**: the domain returns a code and params (`Warning`, `MsgParams` in `src/domain/types.ts`, the month-close problems), never prose, and never imports i18next; the client words it (`warnings.<code>` in `snapshotSelectors.ts`; a `warnings.<code>_<context>` variant needs the base `warnings.<code>` too). Params that are translated themselves go through the formatters of `createI18n` (`{{ym, month}}`, `{{date, day}}`, `{{list, problems}}`)

## Testing

Vitest + jsdom + @testing-library/react in `tests/`. `vitest.config.ts` has projects `node` (`*.test.ts`; the `*.test-d.ts` type assertions are checked by `tsc -b` through `tsconfig.test.json`), `dom` (`*.test.tsx`, `tests/components/`, `tests/pages/`, and `.ts` files in `DOM_TS` that need a DOM), both on `vmThreads`; `sqlite` on `forks` for the `.ts` tests under `tests/server/`, `tests/modules/` and `tests/demo/` (`SQLITE`: they open `node:sqlite` databases, and that work contends across worker threads: the whole suite took 16.3 s with them on `vmThreads`, 7.4 s on `forks`); and `forks` for files needing their own process (`OUTSIDE_VM`). ## src/components

UI components. They do not load data: they get typed props and draw markup on CSS tokens.

### Hierarchy

```
ui/*       primitives (Card, Chip, Avatar, Switch, SectionLabel, Skeleton, Toaster…); tone helpers in ui/types.ts
ui/Dialog + ui/useModalDialog   ← the only <dialog> mechanics (ConfirmDialog is built on it)
ui/usePopover                   ← the only menu mechanics (RadioMenu is built on it)
layout/*   shell: AppShell, Sidebar, TitleRow, Freshness, menus
cards/*    dashboard cards (StatusCard, KpiCell, …); purpose in docs/design-system.md §3
charts/*   ECharts wrappers: echarts.ts (registry), theme.ts (useChartTheme), tooltipHtml.ts (`escapeHtml`)
top level  WarningsBanner, PageError, ErrorBoundary, AuthGate, SetupGate, NotifyProvider
```

- Provider order: `QueryClientProvider` > `AuthGate` (sign-in, end of session; state in `src/lib/authState.ts`) > `SetupGate` (setup wizard while pending) > `AppShell`; a page sits in `ErrorBoundary`. Routes come from `routesFor({ demo })`; `Sidebar` lists `inMenu(routes)`.
- `NotifyProvider` is the source of `useToast()` / `useConfirm()`; the "Records" and "Settings" screens take the hooks, not props.
- Only remarks that distort totals go in `WarningsBanner`; the rest and notices go in `WarningsMenu`.
- `charts/echarts.ts` is `echarts/core` plus an explicit `use([...])` list: a new series type or component must be added there or it fails silently at run time. Render through `echarts-for-react/esm/core` with `echarts={core}` (not `lib/core`: React error 130). Never import all of `echarts`: bundle caps are in `.size-limit.mjs` (`npm run size` after `npm run build`); raising one is a deliberate edit.
- Strings interpolated into a tooltip formatter go through `escapeHtml` (`charts/tooltipHtml.ts`).

### Rules

1. Color is only `var(--…)`. For chips use `toneTextStyle(color)`, for avatars `toneStyle(color)`; do not assemble a background by hand. Text in a semantic color is only `--X-text`.
2. Icons are `@tabler/icons-react`. Draw an icon that comes from a prop or from data through `createElement(icon, { size, stroke, 'aria-hidden': true })` (the `react-hooks/static-components` rule).
3. Charts: `const theme = useChartTheme()` and `<ReactECharts theme={theme} key={theme} … />`. Use `resolveColor('--token')` for a color in options, not `var()`: canvas does not understand CSS variables.
4. The page's main number is a figure at weight 400 (`.hl__value` on Assets, a KPI strip on Loans and Goals); a chip is status only, a change is ink text (`.delta`).
5. Menus and dialogs do not write their own mechanics: `usePopover` and `Dialog`/`useModalDialog`.
6. Type-only imports are `import type { … }` (verbatimModuleSyntax is on).
7. A new component with branching gets a test in `tests/components/`.

## src/lib

Browser-side data access. Numbers are computed in `src/domain/` (shared with the server); this folder only fetches the snapshot and shapes it for pages.

### Files

Per-file descriptions are in the file map; these are the rules.

- `useFinanceData.ts`: `useSnapshot(select?)` is the only snapshot read. After a change the snapshot depends on, call `refreshSnapshot(client)`, never a bare `invalidateQueries`.
- `snapshotSelectors.ts`: pure `FinanceSnapshot → page data`; every page number comes from here (`tests/lib/snapshotSelectors.test.ts`).
- `DashboardContext.tsx`: `fmt()` formats in `snapshot.baseCurrency`; the client never converts.
- `privacy.ts`: `usePrivacy()`; while hidden `fmt()` returns `PRIVACY_MASK`, so dashboard amounts are masked in one place. Records screens mask what they read themselves with `useMoney()` or `usePrivacy()` (journal via `journalLine(e, mask)`); input fields stay unmasked; percentages, months and counts are not masked.
- `formatters.ts`: all numbers and dates go through it (`fmtNum`, `fmtMoney`, `fmtPct`, `fmtMonths`, `fmtCurrency`, `fmtDayNumeric` for every displayed date), never `toFixed`.
- `api.ts`: `apiFetch` (read), `apiSend(url, method, body?)` (write); errors are `ApiError`, translated from `errors.<code>`. `authState.ts` calls `fetch` itself: for `/api/auth*` and `/api/demo/restart` a 401 is an answer, not the end of the session.
- `router.ts`: `useRoute()` / `navigate()`; routes live in `src/routes.ts`. `registerNavigationGuard(() => Promise<boolean>)` returns owner cleanup; `confirmNavigation()` shares the check with setup Back/stepper jumps. A pending question ignores repeated departures. The router adds its position key alongside existing `history.state` object fields, keeps the committed route while Back/Forward returns to the original history position, then replays an approved traversal. An approved internal route also waits for a concurrent browser restoration before committing, preserving the editor’s existing history entry. Replace preserves unrelated state and adds no entry. Browser document departures use native unload handling. Unmount invalidates outstanding owner answers, so auth loss cannot revive a protected route.
- `useUnsavedChanges(atRisk)` returns `confirmDiscard()` and registers one live mounted guard. Dirty, pending and unreadable month/account/loan values and allocation lines activate the native `beforeunload` warning; setup uses local row differences and submission state. `useConfirm` supplies the app question; translations live in main `common.unsaved` keys. Saving clears risk without invalidating an already open question. No local persistent draft storage is used.
- `recordLink.ts`: `recordHref(path, key)` / `recordFromHash()`. The hash is a selection key (`encodeURIComponent`), not an element id; a key naming nothing leaves the usual selection, no error (`tests/lib/recordLink.test.ts`).
- `media.ts` is the only caller of `matchMedia`.
- `themeState.ts`: per-device theme in `localStorage`, every access in try/catch.
- `metricText.ts` renders the metric catalog's keys in the UI language.

### Guarded row mutation boundary

`src/server/db.ts` captures connection ownership, `total_changes()` and `PRAGMA data_version` synchronously in an opaque read token. `guardedBatch` uses `BEGIN IMMEDIATE`, compares both counters before any write, and executes all statements and commit synchronously. Foreign tokens/statements are rejected. Any failure rolls back the whole transaction; async validators never run while the shared connection has an open transaction.

`src/server/mutations.ts` captures the token before the builder's first read and repeats read/validation preflight only after an internal read conflict. Other validation, schema and journal errors propagate without retry. Builders must not write or load post-write views. Draft save/close/reopen use this boundary too; close validates the reviewed revision, ordering and module category caps in the same attempt. The revision digest covers effective rows, typed and scheduled loan inputs, source rows, hints, closures, the `trackFlows` parameter and prerequisite state, excluding timestamps and category lines. Advisor monthView carries the revision internally in its approval hash while preserving tool response keys; close_month recomputes that view and builds close within one guarded attempt, so category/source changes after approval cannot slip between separate transactions. `buildInsertRow`, `buildUpdateRow` and `buildDeleteRow` in `src/server/rows.ts` reuse the existing schema/key/limit checks and produce statements plus their result; public row wrappers commit them and retain their response shapes. Retained valuation and early-payment editors send optional `expectedIdentity` column values with generic PUTs; the builder validates those values against the schema and compares them to the authoritative row in each attempt, returning 409 `row_changed` on a mismatch without writing or journaling metadata. Valuations pin the original property name/year and early payments the original loan name/date. Dedicated loan PUTs require `expectedName` for edits, payoff correction and status actions, checked in every guarded attempt. These original-target checks do not version ordinary field edits. Several planned inserts in a table reserve `nextRowid` once and use consecutive explicit rowids. The existing unguarded batch API and single-row journal revert remain available with their existing semantics.
